# ボードロジックをシステムへ移行 - 現状の問題点

最終更新日: 2025年4月5日

現在のボードロジック実装には、以下のような問題点があります。これらの問題を解決するためにECSアーキテクチャへの移行が計画されています。

## 1. 責任の集中

ボードロジックが単一のモジュール（`board.rs`）に集中しており、単一責任の原則に違反しています。このモジュールは以下の全てのロジックを担当しています：

- ボードの初期化と地雷配置
- セルの公開処理
- フラグ操作の管理
- 勝利条件のチェック
- ゲーム状態管理

これにより、コードの理解が困難になり、修正や拡張の際に副作用が発生しやすくなっています。

## 2. ECSアーキテクチャとの不一致

プロジェクト全体はECSアーキテクチャに移行中ですが、ボードロジックはまだ従来のオブジェクト指向スタイルで実装されています。これにより：

- エンティティとコンポーネントを使用しているが、システム化されていないため、ECSのメリットを十分に活かせていない
- 他のECSベースのコードとの連携が難しい
- コードスタイルの不一致が生じている

## 3. テスト困難性

現在の実装では、ロジックと状態管理が混在しているため：

- ユニットテストが困難
- モックやスタブの作成が複雑
- テストカバレッジが不十分
- エッジケースのテストが不足

## 4. 拡張性の制限

新機能の追加や既存機能の変更が困難です：

- ボードサイズやルールのカスタマイズが難しい
- 新しいセルタイプの追加が複雑
- ゲームロジックの変更が広範囲に影響する
- 特殊ルールの実装が困難

## 5. パフォーマンスの問題

現在の実装には以下のようなパフォーマンス上の問題があります：

- 大きなボードでの初期化が遅い
- 連鎖的なセル公開時の再帰処理によるスタックオーバーフローのリスク
- メモリ効率の低い状態管理
- キャッシュ効率の悪いデータレイアウト

## 6. コードの重複

類似した処理が複数の場所に重複して実装されており、DRY原則（Don't Repeat Yourself）に違反しています：

- セル検索ロジックの重複
- 状態チェックロジックの重複
- エラー処理の重複

これらの問題点を解決するために、ボードロジックをECSパターンに基づいて再設計し、複数の責任分離されたシステムとして実装することが必要です。
